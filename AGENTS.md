# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> ## ⚠️ IL FAUT QUE CE SOIT FLUIDE !
> **Demande expresse de l'utilisateur, intransigeant sur ce point : l'appli ET les réglages doivent réagir TOUT DE SUITE, sans lourdeur, jamais « quelques secondes plus tard ».** Tout changement de code est jugé d'abord là-dessus. Avant d'ajouter un travail dans un aperçu en direct, une peinture, un clic ou une navigation : le mesurer (sonde cProfile, fenêtre de réglages ENTIÈREMENT construite — ~24 000 widgets) et ne rien refaire qui n'a pas changé. Pièges déjà rencontrés (octobre 2026, « avant ils étaient hyper réactifs, maintenant hyper lourds ») : `seed_table_look` (appelé par le restylage de l'inspecteur) refaisait les ~130 tableaux de la fenêtre de réglages à chaque changement (~1 s) — `settings_layout._set_flat_tables_style` ne refait plus rien si rayon / bordure / padding n'ont pas changé (`force=True` pour la famille « tables ») ; l'enregistrement des dimensions relisait tous les tableaux (~0,35 s) — seuls ceux qui ont signalé un changement sont relus (`SettingsWindowV2._schedule_persist_frame`, `_dims_dirty`) ; la fenêtre principale comparait l'aperçu aux réglages appliqués (écritures différentes : au 1er changement tout était rafraîchi, ~2 s) — la v2 lui passe les clés RÉELLEMENT changées (`live_changed_keys` → `_apply_settings(settings, changed_keys)`) ; les zones de saisie restylées en fond le sont par tranches de 6 ms (`settings_theme._restyle_pending_inputs`), plus par paquets de 40 (~40 ms d'un coup). Mesure : premier cran 2-3 s → ~150 ms, crans suivants ~50 ms.

## Projet

Pipeline Browser : navigateur de fichiers en colonnes (Miller columns) en PySide6, pour une arborescence de projets de production (racine par défaut `F:\PIPELINE`, réglable via `root_path` dans `data/pipeline_settings.json`). Application Windows (DPI per-monitor, attributs « caché » Windows, chemins `.exe`) ; le code et les commentaires sont en français. Le dépôt est édité depuis WSL mais l'appli tourne sous Windows.

## Commandes

- Lancer : `pipeline_browser_debug.bat` (crée `.venv`, installe PySide6/ezdxf/matplotlib, lance l'appli) ou `python pipeline_browser.py` (`pythonw` pour éviter la console).
- Dépendances : `requirements.txt` (PySide6 ; optionnels : OpenEXR, numpy, ezdxf, matplotlib).
- Tests (unittest, offscreen Qt, certains exigent Blender installé) :
  - tous : `python -m unittest discover -s tests`
  - un fichier : `python -m unittest discover -s tests -p test_turntable.py`
  - un test : `python -m unittest tests.test_render_log.RenderLogTest.test_requested_columns_and_render_metadata` (lancer depuis la racine ; les tests importent `previews`, `detail_panel`… : patcher un nom dans le module qui l'utilise, pas dans celui qui l'a importé).
- Tout fichier de test commence par `import _isolate` (`tests/_isolate.py` : réglages, presets et état des fenêtres redirigés vers des COPIES temporaires). OBLIGATOIRE pour tout nouveau test : `SaveTest` enregistrait et `update_active_preset` écrivait dans le VRAI fichier de presets — le preset « fab » de l'utilisateur a reçu les valeurs du test (curseurs 20 / 9), rejouées ensuite par-dessus ses réglages (« les sliders changent de style tout seuls », signalé). Doubler des fonctions de presets : les remplacer dans `settings_store` (là où `update_active_preset` les cherche), pas seulement dans le module testé.
- Pas de linter ni de build configuré.
- `.venv/` est ignoré par git (ne pas l'éditer).

## Architecture

Modules plats à la racine (aucun package), en couches : chaque module n'importe que ceux qui le précèdent (les imports tardifs `import browser_core as pb_core` dans `settings_*` évitent le cycle).

Application (ordre de dépendance) :
- `config.py` : constantes (extensions, listes d'omission `GLOBAL_OMIT_*`) ; `ui_state.py` : réglages d'interface **réassignés à l'exécution** (`WINDOW_RADIUS`, `HEADER_HEIGHT`, `STEP_BADGE_STYLE`…). Ils se lisent toujours via `ui_state.X` (jamais `from ui_state import X`, qui figerait la valeur).
- `previews.py` : décodeurs d'aperçus, caches mémoire/disque, rendus Blender/Maya, ordonnanceur de fond, journal de rendu.
- `browser_core.py` : scan disque, config projet/layout/raccourcis, helpers de peinture/redimensionnement.
- `row_delegates.py` (`RowDelegate`, `ProjectTileDelegate`), `column_config.py` (dialogue de configuration des colonnes), `capture_widgets.py` (capture, `_PreviewBlock`, `_ColumnCard`…), `column.py` (`Column`), `preview_column.py` (`PreviewColumn`, export PureRef), `detail_panel.py` (`DetailPanel`, inspecteur).
- `software_launch.py` : ouvrir un logiciel « au bon emplacement ». Dans un set, un logiciel choisi dans la colonne LOGICIELS (dossier reconnu par `software_icon_key`) qui a un lanceur (`LAUNCHERS` : BLENDER, HOUDINI — demandes de l'utilisateur, les autres « au fur et à mesure ») : TOUTES les colonnes ouvertes sous son dossier (dossier = celui du logiciel ou en dessous) ont, juste avant leur punaise, un bouton à son icône (`Column.set_launcher`, créé à la demande ; posé par `PipelineBrowser._sync_software_buttons`, appelé à chaque `add_column`) ; clic = le logiciel s'ouvre dans le dossier de la colonne (`_launch_software`). Blender : lancé (détaché, dossier courant = la colonne) avec un chemin de scène QUI N'EXISTE PAS (`untitled.blend`, puis `untitled_01.blend`… : un fichier existant serait ouvert) ; Blender ouvre la scène par défaut et retient ce chemin (« saving will write to … », vérifié sur Blender 5.2) : Enregistrer sous s'ouvre dans le dossier, rien n'est créé avant l'enregistrement ; il signale au passage qu'il n'a pas pu lire ce fichier (attendu). Le dossier est AUSSI ajouté aux favoris (« Bookmarks ») de sa fenêtre de fichiers (demande de l'utilisateur) : section `[Bookmarks]` de `bookmarks.txt`, lu par Blender au démarrage, écrit juste avant le lancement (`add_blender_bookmark` : une seule fois par dossier, reste du fichier et fins de ligne gardés, écriture par fichier temporaire), NOMMÉ D'APRÈS LE SET (demande de l'utilisateur ; nom du dossier terminal de la chaîne, `_chain_terminal_path`, passé par `_sync_software_buttons` → `launch(clé, dossier, set)`) : ligne `!<nom>` au-dessus du chemin (syntaxe de Blender, vérifiée) ; favori déjà présent = seul son nom est remis à jour. File > OPEN dans ce dossier aussi (demande de l'utilisateur) : tant que la scène n'est pas enregistrée, Blender ouvre la fenêtre d'Open dans le dossier du PREMIER fichier récent (et non dans celui de la scène, contrairement à Enregistrer sous) — la scène est donc mise en tête de `recent-files.txt` avant le lancement (`add_blender_recent` : mécanisme de Blender lui-même, valable pour le menu File, l'écran d'accueil et Ctrl+O ; scènes ajoutées par le lancement précédent et jamais enregistrées retirées, liste tenue dans `data/blender_recent_added.json`, ignoré par git ; reste de la liste et fins de ligne gardés). Houdini (`_launch_houdini`) : `houdini.exe` (licence des préférences de l'utilisateur ; `HOUDINI_EXECUTABLE`, sinon le `bin` de hython) lancé SANS scène, dossier courant = la colonne : une scène sans titre a pour `$HIP` le dossier courant (vérifié sur Houdini 21 avec hython : `<dossier>/untitled.hip`), Enregistrer sous / Ouvrir s'y ouvrent, rien n'est créé. ### Pipeline d'aperçus
Aperçus asynchrones : `_PreviewDecodeManager` / `_PreviewDecodeTask` (QRunnable), `_IdlePreviewScheduler` (rendu en tâche de fond quand l'appli est inactive). Cache disque dans `data/.pipeline_preview_cache/` (clé = chemin + mtime ; métadonnées, nettoyage des caches périmés). Ce dossier compte des dizaines de milliers d'entrées : JAMAIS de `glob` / `iterdir` dessus (~100 ms de Python chacun, GIL tenu par tranches ; un aperçu absent en déclenchait jusqu'à une dizaine — cause principale des saccades de la lecture vidéo et des lenteurs des colonnes pendant le calcul des aperçus d'un dossier) : index des noms `previews._CACHE_INDEX` (`with_prefix`, `with_digest`, `has_png`, lu une fois, relu si le dossier a changé — au plus toutes les 30 s ; nos écritures / suppressions le tiennent à jour : `added` / `removed`). Ménage complet (`sweep_preview_cache`, ~35 s de calcul pour ~10 000 fiches, plantait sur un « accès refusé ») : au plus une fois par jour (`sweep_preview_cache_if_due`, `.last_sweep`), en fond, en rendant la main à chaque fiche ; renommage des anciens noms (`migrate_cache_names`) aussi en fond. Décodeurs par format : OBJ (numpy/QPainter ou Blender EEVEE), Alembic `.abc` et `.blend` (Blender), `.ma` (mayapy), scènes Houdini `.hip`/`.hiplc`/`.hipnc` (hython, `_render_hip_wireframe` : `_HIP_EXPORT_SCRIPT` exporte la géométrie AFFICHÉE de /obj à l'image courante — jamais les objets masqués, trop longs à cuire — en Alembic, ou en OBJ écrit en Python pour les `.hipnc`, qui n'ont pas le droit d'exporter en Alembic ; puis même rendu Blender que les autres fichiers 3D ; test `tests/test_hip_preview.py`), PSD, EXR/HDR/TX (OpenEXR / oiiotool), vidéo, DWG (ezdxf + ODA File Converter ; sans ODA ou si la conversion échoue : vignette BMP/PNG intégrée au DWG par AutoCAD, `_decode_dwg_thumbnail`, test `tests/test_dwg_thumbnail.py`), DXF (dessin vectoriel direct par ezdxf, `_render_dxf_file`, aussi utilisé pour les DWG convertis ; image cadrée sur le plan), brosses Photoshop `.abr` (planche des pointes, parseur maison : versions 1/2 et 6/7/9/10, ordre et pointes rondes calculées lus dans la section `desc`, `_abr_brushes` ; test `tests/test_abr_preview.py`), Illustrator `.ai` (rendu PDF de la 1re planche via QtPdf, planches feuilletables dans l'inspecteur ; sans contenu PDF — page d'avertissement d'Adobe détectée par `ai_has_pdf_content` — ou `.ai` PostScript : vignette JPEG XMP `xmpGImg:image` ; test `tests/test_ai_preview.py`). Les rendus Blender/Maya sont des **scripts Python embarqués dans des chaînes** exécutés en sous-processus (voir `_render_wireframe_eevee`, `_render_ma_wireframe`) — ce code s'exécute dans l'interpréteur de Blender/Maya, pas dans l'appli. Les profils de rendu (low/high…, turntable) viennent de `files/parametres rendus.txt` (`_load_render_profiles`) ; journal de rendu quotidien `pipeline_preview_render_<date>.html` / `.log`.
Les fichiers du cache ont un nom explicite `<set>__<fichier>__<code16>_<mtime>.png` (set = jusqu'à 3 dossiers sous la racine, voir `_cache_label`) ; turntables `<set>__<fichier>__turntable_<code16>`. `migrate_cache_names()` (appelée par `main()`) renomme les anciens noms opaques.

La fenêtre de réglages (surtout la fenêtre « Paramètres généraux », mode `general`, et ses briques : `settings_widgets.py`, `settings_layout.py`, `settings_theme.py`, `settings_colorpicker.py`, gabarits de `over/Notes.txt`) servira de **point de départ aux fenêtres de réglages des futures applications** de l'utilisateur : on copiera ces modules dans la nouvelle appli puis on les fera évoluer là-bas (pas de paquet partagé pour l'instant). - Garder le moteur (widgets, sections, tableaux, rôles de texte, arrondis, construction de haut en bas, réutilisation de la fenêtre) **séparé des réglages propres à Pipeline Browser** (colonnes, étapes, logiciels, aperçus, racine de projets).
- Ne pas ajouter de nouvelle dépendance de `settings_*` vers du code propre à l'appli (`browser_core`, `column`, `previews`…) ; passer par des paramètres, des signaux ou un module de réglages dédié.
- Pour un nouveau réglage, déclarer clé, type, défaut et libellé de façon générique plutôt que de coder la clé en dur dans la logique commune.
- Quand l'utilisateur démarre une nouvelle appli à partir de cette fenêtre : demander le chemin de ce projet, copier ce qui est utile, retirer les sections propres à Pipeline Browser, et noter l'origine de la fenêtre dans l'`AGENTS.md` de la nouvelle appli. Réfléchir à la structure de la nouvelle appli (couches, modules) avant de coder.

## Conventions du projet

**Styles : jamais inventés.** Tout élément qui a déjà son équivalent dans les réglages (tableau, titre, zone de saisie, toggle, panneau…), y compris dans la fenêtre principale, est construit AVEC les briques des réglages (`settings_window_v2.seed_window_look` puis `_flat_cells_table` / `build_cells_table`, rôles de texte, `_title_font`, `_PanelFrame` + `M`, `make_field`) ; précédents : `settings_quick_style.QuickStyleWindow`, `focus.FocusInfoPanel`. Demande expresse de l'utilisateur, valable pour tout élément à venir.

`over/Notes.txt` définit des **gabarits** pour les lignes de la fenêtre de réglages, à appliquer à toute ligne existante ou future du même type sans que l'utilisateur le répète :
- Lignes *police* : une seule ligne ; toggles app/système sans texte, collés au menu déroulant ; toggle « gras » avec le texte « gras » avant (les deux états) ; texte « Hauteur » avant le slider.
- Lignes *arrondi des angles* : une ligne, pas de bouton copier, toggle « lier les 4 » (texte avant, les deux états), 4 sliders avec champ de saisie, valeur mise à jour en temps réel.
- Lignes *bordures* : pas de bouton copier, toggle « lier les 4 », 4 toggles chacun au-dessus du choix de couleur de son côté.
Styles de la fenêtre de réglages — une seule source par type d'élément, jamais de style posé à la main :
- Textes : un **rôle** (`TEXT_ROLES` dans `settings_theme.py`, appliqué par `_set_text_role` / `_text_label`). Changer l'apparence d'un type de texte = modifier son rôle, pas les sites d'appel.
- Arrondis des zones de saisie et des boutons : chaque widget s'inscrit à sa création (`_register_input` / `_register_radius`) et suit le réglage tout seul. Un nouveau widget habillé en zone de saisie doit s'inscrire ; ne jamais tenir de liste de champs à mettre à jour.
- Tableaux : tous ont un entête (`_ResizableTableHeader` : sélection de colonnes Maj+clic, toggle « largeurs égales »). `_build_flat_table` / `_build_override_flat_table` ajoutent eux-mêmes l'entête Paramètre|Valeur (`_attach_flat_head`) et s'inscrivent (`_register_flat_table`) ; les tableaux à cellules (Icônes, Logiciels) passent par `_register_cells_table`. Arrondi, bordure, padding et couleur d'entête passent par `_set_flat_tables_style` / `_TABLE_HEAD`.
- Dimensions : la bordure droite de chaque `_TableFrame` est agrippable (largeur du tableau, collé à gauche au niveau du titre) ; largeur du tableau + largeurs de colonnes sont enregistrées dans `table_dims` (clé = titres des sections + rang, voir `_TableFrame.dimsKey`).
- Vérification : `tests/test_settings_window.py` (aller-retour des valeurs, suivi des styles) et `tests/_probe_compare.sh` (captures de toutes les pages avant/après, comparées au pixel ; `tests/_probe_diff.py` localise les différences).

Lire `over/Notes.txt` en entier avant de modifier la fenêtre de réglages (`over/Prompts.txt` contient l'historique des demandes).

## Commit et push

- Commit depuis WSL avec `git` (identité globale déjà configurée) ; `git add -u` pour les fichiers suivis, `lancer.sh` (non suivi) n'est pas à ajouter.
- Le push se fait avec `git.exe push` (Git for Windows, via le Gestionnaire d'identifiants Windows) : un `git push` WSL échoue (« could not read Username for 'https://github.com' »). Sinon, pousser depuis un terminal Windows dans le dossier.
- Messages de commit en français, terminés par la ligne `Co-Authored-By` demandée par l'environnement.
