# Color-managed image display parity: Lightroom vs. the PySide6 application

## What the profiles and color pipeline mean

### Takeaway
An RGB triplet has no unique visual meaning without a source color space. Matching Lightroom requires matching both the rendered image and the transforms from its source profile through the display profile; merely attaching an ICC profile to a `QImage` does not convert its pixel values or establish monitor-aware widget output.

### Cited Findings
- ICC profiles characterize input/output devices and color spaces and enable a color management system to translate color data between device spaces through a profile connection space. Embedded profiles tell software how to interpret the associated image data. [ICC: Introduction to the ICC profile format](https://www.color.org/getting-started/)
- An ICC profile describes primaries/white point and tone response; Qt describes a color space as primaries plus a transfer function. sRGB has the sRGB transfer function, Adobe RGB (1998) uses gamma 2.2, ProPhoto RGB is a very wide gamut, and Qt 6.8+ also names BT.2020, PQ and HLG spaces. [Qt: QColorSpace](https://doc.qt.io/qt-6/qcolorspace.html)
- Assigning a profile and converting are different operations. Qt documents `QImage::setColorSpace()` as setting the image's color-space metadata “without performing any conversions”; `convertToColorSpace()` transforms the image data and does nothing when the source image has no valid color space. [Qt: QImage](https://doc.qt.io/qt-6/qimage.html)
- `QColorSpace::fromIccProfile()` can represent ICC profiles, but Qt documents limits on supported profiles (RGB/Gray in current Qt 6 docs); an unsupported profile produces an invalid color space, while the original profile bytes remain accessible. [Qt: QColorSpace](https://doc.qt.io/qt-6/qcolorspace.html)
- Lightroom Classic's Develop view uses ProPhoto RGB by default; other listed modules primarily use Adobe RGB. Lightroom also uses the monitor profile to translate image colors to the monitor, and offers soft proofing to simulate a destination profile. These are Lightroom working/display pipeline details, not a claim that its source photo is stored as ProPhoto RGB. [Adobe: How to manage color in Lightroom Classic](https://helpx.adobe.com/lightroom-classic/desktop/workspace/color-management.html)
- Lightroom's raw Profile control affects color and tonal rendering. Adobe Color is the default for imported raw color photos; Camera Matching profiles are camera-model based and intended for a rendering closer to the camera's JPEG/display look. These raw rendering profiles are conceptually distinct from an embedded RGB ICC profile on a rendered JPEG/TIFF. [Adobe: Work with image tone and color](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/image-tone-color.html)
- Lightroom's export color-space choice converts the rendered image to the selected space and tags it; Adobe recommends 16-bit ProPhoto RGB when preserving editing color detail. Exporting sRGB is a useful controlled interchange test, but it is not equivalent to Lightroom's Develop rendering. [Adobe: Lightroom Classic reference](https://helpx.adobe.com/pdf/lightroom_reference.pdf)
- The ICC rendering intent controls how colors outside the destination gamut are reproduced; the ICC specification defines perceptual, media-relative colorimetric, saturation and ICC-absolute colorimetric intents. Thus wide-gamut colors can differ after conversion even when profiles are honored, especially where the destination display cannot reproduce them. [ICC profile specification](https://www.color.org/icc1-v41.pdf); [Microsoft: Rendering intents](https://learn.microsoft.com/en-us/windows/win32/wcs/rendering-intents)

### Inferences
- An Adobe RGB or ProPhoto RGB file displayed as though its channel values were sRGB will usually look different from a color-managed rendering. It is an interpretation error, not evidence that the file's RGB values changed.
- A raw file may have no ordinary embedded RGB output profile for its sensor mosaic. Lightroom's chosen raw profile, white balance, edits and rendering determine the resulting pixels. Compare against the same rendered preview/export before attributing a difference to monitor color management.
- A camera-matching profile difference can be large even when both applications ultimately display on the same correctly profiled monitor: it changes the raw-to-rendered image before the monitor transform.

### Gaps
- Adobe's public documentation does not specify the exact internal CMM, rendering intent, or per-stage pixel format used by every current Lightroom Classic view. Treat the documented working-space/module behavior as authoritative, not as a promise that all views are pixel-identical.
- `QImageReader` format plugins can differ in which metadata they expose and how they decode a given format. Verify `QImage.colorSpace()` and the actual ICC bytes for the file formats used here rather than assuming every plugin preserves every profile.

## What Qt and Windows do at display time, and the diagnostic/fix order for this codebase

### Takeaway
The most likely causes here are an unlike rendered source (Lightroom preview vs. original/fallback), an embedded profile being ignored or lost in an 8-bit cache path, and different monitor-profile handling. Windows HDR/wide-gamut behavior and bit-depth loss matter when those modes/content are involved, but are lower-priority explanations for an ordinary SDR sRGB image.

### Cited Findings
- `QImageReader` decodes supported image formats into `QImage`; it exposes decoding controls such as scaling and orientation. Qt's documentation does not state that `read()` converts decoded pixels to the active monitor profile. Use `QImage.colorSpace()` to inspect the color space reported on the decoded image. [Qt: QImageReader](https://doc.qt.io/qt-6/qimagereader.html); [Qt: QImage](https://doc.qt.io/qt-6/qimage.html)
- Qt provides explicit source-to-target transforms (`QColorTransform`, `QImage::convertToColorSpace()` / `colorTransformed()`). This is distinct from changing the image's metadata. `QPixmap` and `QPainter` are drawing/storage facilities; Qt's public widget-painting documentation does not document automatic per-monitor ICC conversion for ordinary `QWidget` painting. [Qt: QColorSpace](https://doc.qt.io/qt-6/qcolorspace.html); [Qt: QImage](https://doc.qt.io/qt-6/qimage.html); [Qt: QPainter](https://doc.qt.io/qt-6/qpainter.html)
- Windows has long provided ICM/WCS APIs for applications to perform color management; historically, most apps/content assumed sRGB and the OS did not color-manage every legacy app. Windows Advanced Color/Auto Color Management on supported displays can manage colors for apps system-wide. [Microsoft: DirectX and Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range)
- When Advanced Color is active, display ICC behavior changes. The Windows 11 legacy display-ICC compatibility helper is per executable and not enabled by default; if active, the app is expected to color-manage to the synthetic display profile and Windows then converts the process output. This can cause double transforms if an app and OS path are both assumed without checking. [Microsoft: ICC profile behavior with Advanced Color](https://learn.microsoft.com/en-us/windows/win32/wcs/advanced-color-icc-profiles)
- Windows Advanced Color uses FP16 composition and can expose higher display precision; in the older non-Advanced-Color desktop path, DWM output was limited to 8 bits per channel. Higher precision reduces banding, but does not fix a wrong source-profile interpretation. [Microsoft: DirectX and Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range)
- HDR requires more than a wide gamut: transfer functions and luminance encoding matter. Qt lists BT.2100 PQ and HLG encodings; Adobe documents that Lightroom HDR has HDR-specific color spaces, display support and SDR tone mapping, and that an SDR rendition must be tone-mapped. [Qt: QColorSpace](https://doc.qt.io/qt-6/qcolorspace.html); [Adobe: Edit and Export in HDR](https://helpx.adobe.com/lightroom-classic/desktop/process-and-develop-photos/hdr-output.html)
- In this repository, `previews.py` decodes ordinary 2D images through `QImageReader`, then converts results to `QPixmap` and disk/memory preview caches. `focus.py`'s focus loader explicitly converts images to `Format_RGB32` or `Format_ARGB32_Premultiplied`. The PySide6 installation inspected for this research is 6.9.1 / Qt 6.9.1. The project dependency is unpinned (`requirements.txt` says `PySide6`), so behavior must be checked against the runtime actually deployed.
- Lightroom-managed folders have a separate preview path in `lightroom_bridge.py`: the app requests/loads Lightroom-generated proxy JPEGs, with a local application-rendered fallback when appropriate. A displayed proxy is a rendered preview, not necessarily the source file or Lightroom Develop's current full-resolution output.

### Inferences
- `Format_RGB32` stores 8 bits per RGB channel (32 bits total including the unused alpha byte); `Format_ARGB32_Premultiplied` stores 32-bit ARGB. The explicit conversion in `focus.py` therefore discards higher source precision before display. This can contribute to banding/tonal differences, but is unlikely to explain a substantial hue/saturation mismatch in a normal SDR photo by itself. [Qt: QImage formats](https://doc.qt.io/qt-6/qimage.html)
- The combination of `QImageReader` → 8-bit format conversion → `QPixmap` → PNG/JPEG preview caches creates several points where profile metadata may be absent or where a wide-gamut image may be shown without an intentional conversion. The current source has no explicit `QColorSpace`/`convertToColorSpace` handling in the searched image-display paths.
- A color-managed Lightroom Develop view compared with an unmanaged Qt widget may diverge on a wide-gamut display even for the same decoded pixels. On a conventional sRGB display and an embedded-sRGB SDR JPEG, parity is a reasonable first baseline.
- If the mismatch appears only with HDR enabled, HDR/WCG mode, content transfer function, the SDR white level and tone mapping become high-priority variables. Ordinary 8-bit SDR preview handling is not a complete HDR pipeline.

### Practical diagnostic and fix order
1. **Establish a same-content baseline.** Export the Lightroom-edited photo as SDR, 8-bit sRGB with the ICC profile embedded. Open that exact exported file in Lightroom and this app on the same display. Do not compare a raw Develop rendering to the app's RAW-embedded JPEG or a small catalog proxy. If these match, the original gap is upstream in raw profile/edit/proxy selection rather than Qt display.
2. **Record each preview's provenance.** For a failing path, record whether the app displayed the original, Lightroom catalog proxy, or application fallback; check for stale disk caches. In this codebase inspect the branches in `lightroom_bridge.py` and `previews.py` first. Delete/rebuild only the relevant preview cache through the app's existing mechanism after capturing the current behavior.
3. **Probe profile metadata at every boundary.** Log `QImageReader.read().colorSpace().isValid()`, `.description()`, `.primaries()`, `.transferFunction()`, pixel format and ICC profile byte length; repeat after `convertToFormat`, `QPixmap.fromImage(...).toImage()`, and reading any generated preview from disk. Use sample files tagged sRGB, Adobe RGB and ProPhoto RGB, plus an untagged file. Do not infer that an 8-bit pixel format is sRGB.
4. **Separate metadata from conversion.** Preserve a valid embedded source profile, then explicitly convert image pixels to the intended display/interchange space. For a normal SDR QWidget viewer, an explicit sRGB-normalized image path is a practical baseline: use `convertToColorSpace(QColorSpace(QColorSpace.SRgb))` only when the source profile is valid; define and document a policy for untagged files (usually assume sRGB for common web/photo formats). Do not call `setColorSpace(sRGB)` on Adobe RGB pixel values as a substitute for conversion.
5. **Verify monitor handling in the actual Windows mode.** Confirm the correct ICC profile is assigned to the physical display in Windows Color Management, then compare Lightroom and the app with Advanced Color/HDR state recorded. Check the executable's Compatibility setting for “Use legacy display ICC color management.” Choose one defined route: rely on supported Windows Auto Color Management, or implement app-level monitor conversion with an ICC CMM/appropriate Windows pipeline. Avoid double-applying the monitor transform. Repeat for every monitor because profiles are per display.
6. **Investigate precision and HDR only after SDR parity.** Compare an 8-bit sRGB test first. If the issue is banding, inspect source precision and each conversion/cache format; if it is an HDR-only luminance/contrast gap, verify HDR mode, PQ/HLG or HDR color-space metadata, GPU path, SDR white/tone mapping, and whether this Qt widget pipeline actually presents HDR content. Qt's availability of FP16 formats and PQ/HLG `QColorSpace` values alone does not make the widget pipeline HDR-aware.
7. **Implement and verify the narrowest fix.** Centralize image normalization at decode/cache ingress so the focus viewer, columns, detail panel and Lightroom-proxy path receive consistent color-space metadata and intended SDR pixels. Keep wide-gamut/HDR as an explicit separate path if required. Check rendered values with a profile-tagged test chart and compare the same on-screen area; screenshot pixel capture is useful for detecting app-to-app pipeline differences but is not a substitute for a colorimeter measurement.

### Gaps
- Qt's documentation establishes image transforms and color-space metadata APIs but does not promise that ordinary PySide6 `QWidget`/`QPixmap` output is converted through the Windows monitor ICC profile. Confirm this empirically on the deployed Qt 6.9.1 build and Windows configuration; do not treat forum reports as an API contract.
- The codebase's Lightroom SDK/plugin response implementation and generated JPEG profile tagging were not fully audited here. Determine the profile bytes on the actual Lightroom proxy and fallback files before assigning that stage as the root cause.
- No colorimeter measurements, affected sample files, monitor model/profile, Windows build, HDR state, or Lightroom comparison module were supplied. The cause ranking is therefore a diagnosis order, not a finding that one specific cause is proven.
